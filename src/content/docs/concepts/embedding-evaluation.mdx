## Definition and intuition

Embedding evaluation tests whether vector distances support the intended task on unseen examples.

Chapter 10 trains representations by choosing which examples should be close or far apart. The construction of positive and negative pairs is part of the learning objective.

## Before you start

Read [Text Embedding](/llm-concept-atlas/concepts/text-embedding/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **embedding evaluation** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Define a benchmark of queries, pairs, or triplets with judgments
2. **Transform:** Compute task-relevant ranking or similarity metrics
3. **Inspect:** Inspect errors by domain and compare with a simple baseline.

### The important distinction

A benchmark should match the intended operation: sentence similarity, pair classification, or ranked retrieval. For search, retain query-to-document relevance judgments and report top-k performance. Check performance by topic and document length because an average can hide failures on the cases users care about.

## Worked example

An embedding model may score well on general sentence similarity but rank policy passages poorly. A small labeled retrieval set reveals the mismatch. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
relevant = {"A", "C"}
ranking = ["B", "A", "C"]
k = 2
recall_at_k = len(relevant & set(ranking[:k])) / len(relevant)
print(recall_at_k)
```

**Expected output:**

```text
0.5
```

**What the code shows:** The numerator counts relevant IDs in the first `k` results; the denominator counts all judged relevant IDs. Changing `k` changes what the metric asks. The [official chapter 10 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter10) develops the corresponding model-based implementation.

## When to use it

Use it before choosing an encoder and after changing pairs, pooling, or domain data. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- A single benchmark may not reflect the application's documents or answer requirements.
- **Failure to look for:** Reported similarity improves while top-k retrieval of answer-bearing passages worsens.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
