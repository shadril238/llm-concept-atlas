## Definition and intuition

Dense retrieval encodes queries and passages as numerical vectors and retrieves nearby passage vectors from an index. The encoder, pooling, normalization, metric, and indexed text jointly define the retrieval contract.

Read this lesson as a sequence: identify the input, follow the transformation, inspect the result, and explain a failure. The worked example and recorded lab below make those boundaries visible.

## How it works

### The actual representation contract

L12 loads a pinned all-MiniLM-L6-v2 checkpoint, tokenizes each title-plus-chunk input, masks padding during mean pooling, and L2-normalizes the result. Each passage vector has 384 coordinates. Inputs exceeding the declared cap are rejected instead of silently losing their end. Both queries and documents use this symmetric encoder contract; other models may require different query/document prefixes.

### Index scores and directions

A real sklearn brute-force nearest-neighbor index stores the normalized vectors. Its cosine distance is converted to similarity with score = 1 − distance, so larger scores rank first. Independent PyTorch dot products verify the returned scores. For unit vectors only, squared Euclidean distance equals 2 − 2·cosine; an unnormalized L2 index is a different contract. Exact search here is inspectable, while approximate indexes trade work for possible recall loss at larger scale.

### Persistence and adaptation

The index vectors and metadata are saved and reloaded, and neighbor IDs are checked on the reloaded index. Metadata includes chunk order, checkpoint revision, pooling, metric, and input cap; a bare vector file is insufficient. Retrieval-specific adaptation uses positive query/passage pairs and suitable negatives to move task-relevant pairs together. L12 performs no training; the later training phase must evaluate that change on untouched queries.

The complete local/CI implementation and execution contract are linked immediately below.

{/* example:e6-dense-retrieval:start */}

```python
import json
from pathlib import Path
data = json.loads(Path('src/data/retrieval-results.json').read_text())
import math
example = data['retrieval']['numerical_example']
query = example['query_vector']
assert abs(sum(x*x for x in query)-1)<1e-5
scores = [(row['id'],sum(a*b for a,b in zip(query,row['vector']))) for row in example['passages']]
print('actual query width:',len(query))
for id,score in sorted(scores,key=lambda row:(-row[1],row[0])):
    print(id,round(score,4))
print('scope:',example['scope'])
```

## When to use it

Use dense indexes when relevant passages use semantic variation and repeated search should reuse document encodings. Version the entire representation contract and re-embed documents when it changes.

## Limits and common mistakes

A different checkpoint, pooling rule, prefix, or normalization changes the vector space. An approximate search miss and an encoder relevance error are distinct failures. More vectors or a larger encoder do not replace corpus coverage, relevance judgments, or query-specific checks.

## Check your understanding

<details>
<summary>Why is 1 − distance used here?</summary>

The selected index reports cosine distance. Converting it makes the published similarity increase with closeness; treating distance as a larger-is-better score would reverse the ranking.

</details>

<details>
<summary>Can a new encoder reuse the old vectors because both have 384 coordinates?</summary>

No. The coordinates belong to a learned space. Re-embed the collection and bind the new index to its model/pooling contract.

</details>
