## Definition and intuition

Reranking scores a small candidate set more carefully, often by reading each query-passage pair jointly.

Chapter 8 separates finding evidence from using evidence. Evaluate retrieval and answer support independently because a fluent answer can still lack a trustworthy source.

## Before you start

Read [Dense retrieval](/llm-concept-atlas/concepts/dense-retrieval/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **Reranking** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Retrieve a broad candidate pool with a fast first stage
2. **Transform:** Score each query and passage together with a more expensive model
3. **Inspect:** Reorder results and evaluate whether relevant evidence rises.

### The important distinction

A cross-encoder jointly reads a query and passage, so it can notice fine-grained relationships a bi-encoder score misses. Its cost grows with the number of candidates scored per query. Tune the first-stage candidate count for recall before judging the reranker itself.

## Worked example

A dense search returns library hours third. A cross-encoder sees the full question and the Saturday-hours passage together and moves it first. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
query = {"saturday", "hours"}
docs = {"A": {"saturday", "hours", "library"}, "B": {"laptop", "loans"}}
scores = {name: len(query & words) for name, words in docs.items()}
print(sorted(scores, key=scores.get, reverse=True))
```

**Expected output:**

```text
['A', 'B']
```

**What the code shows:** The set intersection produces a simple keyword-overlap score for each document. A dense retriever replaces these sets with learned vectors and a suitable similarity measure. The [official chapter 8 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter08) develops the corresponding model-based implementation.

## When to use it

Use reranking when first-stage recall is acceptable but result order needs improvement. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- It cannot recover evidence that never entered the candidate pool and adds latency.
- **Failure to look for:** The right passage was absent from the first 20 candidates, so reranking cannot find it.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
