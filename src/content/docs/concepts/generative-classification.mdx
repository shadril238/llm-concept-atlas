## Definition and intuition

Generative classification asks a text generator to emit a label or structured answer for an input.

Chapter 4 compares classification with specialized encoders, reusable embeddings, and generators. Label definitions, labeled data, and evaluation examples determine which approach fits.

## Before you start

Read [Generative Model](/llm-concept-atlas/concepts/generative-model/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **generative classification** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Specify allowed labels and decision rules in the prompt
2. **Transform:** Generate a short response, preferably with constrained output
3. **Inspect:** Validate the result against the schema and a held-out test set.

### The important distinction

A generator estimates a sequence of output tokens, not an abstract class variable. Constraining its output to an exact label reduces parsing failures, while a separate evaluator measures label correctness. Prompt examples can improve boundary cases but may also anchor the model to their wording.

## Worked example

A support assistant reads a message and returns `billing` or `technical`. A validator rejects “I think this is billing” when only an exact label is allowed. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
instruction = "Return one label: positive or negative."
example = "Text: I loved it. Label: positive"
query = "Text: The ending was dull. Label:"
prompt = "\n".join([instruction, example, query])
print(prompt)
```

**Expected output:**

```text
Return one label: positive or negative.
Text: I loved it. Label: positive
Text: The ending was dull. Label:
```

**What the code shows:** The final string contains the instruction, demonstration, and new query in that order. Inspect the rendered string before sending it to a real generator. The [official chapter 4 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter04) develops the corresponding model-based implementation.

## When to use it

Use it when labels need rich instructions or when one generator already handles multiple tasks. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- Free-form output can be verbose, inconsistent, or sensitive to prompt wording.
- **Failure to look for:** A model invents a fourth class despite a three-class schema, and downstream code silently accepts it.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
