## Definition and intuition

RAG evaluation measures retrieval quality and generated answer quality as separate parts of one system.

Chapter 8 separates finding evidence from using evidence. Evaluate retrieval and answer support independently because a fluent answer can still lack a trustworthy source.

## Before you start

Read [Retrieval-Augmented Generation](/llm-concept-atlas/concepts/rag/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **rag evaluation** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Assemble questions with known evidence and expected answer constraints
2. **Transform:** Measure whether retrieval supplies supporting passages
3. **Inspect:** Review answers for correctness, citation support, and useful abstention.

### The important distinction

Evaluate the pipeline with a table of question, expected evidence IDs, and acceptable answer facts. Measure retrieval recall before asking whether generation is supported. A correct answer produced without the retrieved evidence can be a lucky guess and should not count as grounded success.

## Worked example

For 20 policy questions, retrieval finds the right passage for 18, but two generated answers contradict their passages. Retrieval success and answer support are different scores. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
relevant = {"A", "C"}
ranking = ["B", "A", "C"]
k = 2
recall_at_k = len(relevant & set(ranking[:k])) / len(relevant)
print(recall_at_k)
```

**Expected output:**

```text
0.5
```

**What the code shows:** The numerator counts relevant IDs in the first `k` results; the denominator counts all judged relevant IDs. Changing `k` changes what the metric asks. The [official chapter 8 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter08) develops the corresponding model-based implementation.

## When to use it

Use it before relying on a RAG assistant and after any corpus or model change. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- One aggregate score can conceal unsupported answers or weak retrieval on rare cases.
- **Failure to look for:** A fluent response is counted correct even though its citation does not contain the asserted fact.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
