## Definition and intuition

Summarized memory compresses earlier conversation into generated notes that are supplied to later calls. It can preserve distant information within a smaller prompt, but compression and repeated rewriting can lose or distort facts.

A summary is an output of a model, with its own prompt, budget, and errors. Reusing it as memory can carry those errors into every later answer. The original messages remain the audit reference.

## How it works

### A real update process

L11 first summarizes the initial four messages, then asks a second real model call to update those notes using the remaining four. Each update has an eighty-token output cap. The final policy combines the generated running summary with the last two verbatim turn pairs. This is actual generated compression, not an ideal hand-authored memory string.

### Corrections and provenance

The user initially says Friday and later corrects the meeting to Monday. A faithful summary should preserve the current value and enough provenance to avoid treating both as equally current. The model may instead repeat earlier text, omit the project code, or invent a request. Both raw summary updates and their exact inputs are shown so these errors can be attributed.

### Fit and evaluate

At each final-answer budget, the packer may remove the summary before dropping recent pairs if the input is too long. The artifact records whether it survived. Actual final answers are graded against three original facts; literal fact presence and stale-value presence are separate diagnostics. Summary-generation token work is recorded separately and should be included when estimating the total application cost.

## Worked example

The recorded second summary invents a request for a new code rather than faithfully retaining LARK-27. At the larger budget the summary policy answers none of the three fields correctly while the buffer gets all three. This failure is an important learning result: compressed context is useful only if its information survives and the answering model uses it.

```python
reference = {"code": "LARK-27", "day": "Monday", "units": "metric"}

for field, value in reference.items():
    print(field, "literal present:", value.casefold() in notes.casefold())
print("stale Friday present:", "friday" in notes.casefold())
```

## When to use it

Use summaries when conversation length outgrows a useful window and the required facts can be checked. Preserve source messages, correction rules, and summary versions; compare against structured memory or retrieval for facts that must not be lost.

## Limits and common mistakes

Compression is lossy, model errors can accumulate, and summary calls add work. Literal presence is not semantic correctness. The lab’s small model failure does not establish that every summarizer is worse than a buffer.
