## Definition and intuition

Pretraining learns a broad next-token distribution from a large corpus. Supervised fine-tuning (SFT) adapts a pretrained generator using examples of a requested behavior and its desired completion. Preference tuning then changes relative response preferences; it does not supply another ordinary next-token target for the same loss.

## Before you start

Read [language models](/llm-concept-atlas/concepts/llm/). Open the [generation training path](/llm-concept-atlas/paths/from-instructions-to-preferences/) if these prerequisites are unfamiliar. Distinguish a token distribution, a trainable parameter, and a task score before tracing this mechanism.

## Theory: how it works

### Full fine tuning

Full fine-tuning updates all selected model parameters, including embeddings, transformer blocks, normalization and output projection. It offers more freedom than a small adapter and needs gradients and optimizer state for far more weights. “Full” describes the updated parameter set, not how much text receives loss. A full model can still use completion-only supervision. Conversely, LoRA can be trained with an inappropriate all-token mask.

### Instruction data templating

An instruction row separates task, optional context, and reference response. Serialization turns these fields into tokens. Native chat models have a particular control-token grammar; ordinary strings such as `### Response:` are not interchangeable with that grammar. Use a native tokenizer's `apply_chat_template` for its intended model, inspect `tokenize=True`, and avoid adding the same special tokens again. An inference generation prompt opens an assistant turn; a completed training example must contain the answer and its end marker.

Our small Pythia model is a base language model with no native chat template. L21 deliberately defines an ordinary-text completion format, encodes the prompt and answer separately, and appends one actual EOS. It never claims to reproduce TinyLlama's chat grammar. Token boundaries are part of this explicit contract. Data content that says “ignore the instruction” remains context data, not a new program instruction.

Completion-only cross entropy sums negative log probabilities at answer/EOS positions and divides by their supervised token count. With causal shifting, the final prompt position predicts the first answer token. `-100` excludes a label from the loss; the attention mask separately excludes padding from attention. When pad and EOS share an ID, masking every occurrence of that ID would remove the real stopping target. L21 rejects an overlength example instead of silently deleting its whole answer.

## Worked example

For prompt IDs `[11,12,13]`, answer IDs `[21,22]`, EOS `0` and two padded positions, the label row is `[-100,-100,-100,21,22,0,-100,-100]`. The model still reads the prompt. Only answer and genuine EOS targets teach the requested output. Three answer targets are not eight training examples.

L21 starts full fine-tuning and LoRA from the identical pinned Pythia checkpoint, using the same 32 training contexts and eight validation contexts. Batch two with two accumulated microbatches gives four examples per optimizer update. Selection compares trained checkpoints every ten steps; the original baseline remains a separate comparator and can outperform the selected trained route.

## Implement it

This standalone Python 3 calculation uses only the standard library. It does not download or train a model. The [complete generation labs](/llm-concept-atlas/labs/generation-adaptation/) provide the pinned environments, actual training entrypoints, staged notebooks, raw results and artifact checks.

```python
prompt_ids = [11, 12, 13]
answer_ids, eos_id, pad_count = [21, 22], 0, 2
ids = prompt_ids + answer_ids + [eos_id] + [eos_id] * pad_count
labels = [-100] * len(prompt_ids) + answer_ids + [eos_id] + [-100] * pad_count
for position, (token, label) in enumerate(zip(ids, labels)):
    print(position, token, "ignored" if label == -100 else "target")
assert labels[5] == eos_id and labels[-1] == -100
```

## When to use it

Use SFT to learn a stable output format, concise extraction style, or domain response policy when representative demonstrations exist. First try a prompt or retrieval baseline if facts change frequently: SFT is not a database update mechanism. The instructional fixture is tiny and does not establish general chatbot capability.

## Limits and common mistakes

The evaluated instruction subset has 32 training,8 validation and 8 test source contexts. Pretraining overlap is unknown. Repeated views of these test outputs are not a new independent benchmark. Preserve failed and length-limited answers, exact base/tokenizer identity and data provenance when transferring the workflow. The book's larger TinyLlama/CUDA settings require their own supported hardware execution; the small profiles do not certify them.

<details>
<summary>If every EOS token is masked because its ID equals the pad ID, what behavior stops receiving supervision?</summary>

The real end-of-answer target disappears. Padding must be masked by position/attention, while the actual EOS remains a completion target.

</details>

<details>
<summary>Does full fine-tuning necessarily beat LoRA on eight heldout contexts?</summary>

No. More trainable capacity changes flexibility and overfitting risk. Compare heldout task outputs, loss and resource cost, with larger fresh evaluation before generalizing.

</details>
