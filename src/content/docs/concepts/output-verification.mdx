## Definition and intuition

Output verification checks that a generated result meets schema, evidence, and task constraints.

Chapter 6 treats a prompt as a task specification. A prompt can guide output, but it does not change model weights or guarantee that an answer is correct.

## Before you start

Read [Instruction prompting](/llm-concept-atlas/concepts/instruction-prompting/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **output verification** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Specify measurable requirements before generation
2. **Transform:** Validate syntax and factual support separately
3. **Inspect:** Reject, retry, or hand off failures with a clear reason.

### The important distinction

Validation has layers: parse the structure, check allowed values, test task logic, and verify factual support against sources. Passing one layer does not imply passing the next. A retry loop should have a cap and preserve the reason for rejection so failures remain visible.

## Worked example

A generated label must be one of three permitted strings. Passing that parser proves shape only; a reviewer still needs examples to assess whether the label is correct. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
allowed = {"positive", "negative"}
candidate = "positive"
print(candidate in allowed)
print("retry or flag" if candidate not in allowed else "accept shape")
```

**Expected output:**

```text
True
accept shape
```

**What the code shows:** Membership in an allowed set checks the shape of one output. It does not determine whether the label was the right one for a particular text. The [official chapter 6 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter06) develops the corresponding model-based implementation.

## When to use it

Use it whenever model output drives code, citations, decisions, or published text. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. ## Limits and common mistakes

- Syntactic validity and factual correctness are different tests.
- **Failure to look for:** Valid JSON contains a fabricated date and passes the parser without a source check.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
