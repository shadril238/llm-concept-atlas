## Definition and intuition

Output verification checks a generated artifact against explicit requirements. Parsing, schema validation, factual correctness, and application acceptance are separate questions that need different evidence.

A JSON object can be perfectly valid and describe the wrong order. Conversely, an informal sentence can communicate the right idea while being unusable by a strict downstream parser. A reliable interface names which contract it checks.

## How it works

### Layer the checks

L09 first parses the entire JSON output and rejects duplicate keys, trailing text, missing or extra fields, invalid item/priority enums, and quantities outside one through nine. Quantity must be an integer, with booleans and decimal representations rejected by the Python contract. It then compares the validated object against the independently authored reference for that case.

### Define the source of truth

The extraction reference comes from the original fixture and is not supplied as a gold-only decoding domain. For arithmetic, a declared answer parser extracts a complete integer or terminal Answer line before comparison. A format score does not measure every human interpretation of prose. For Game 24, exact arithmetic and input-leaf accounting independently check a proposed expression.

### Verification is a decision boundary

A failed contract should produce an explicit invalid or review outcome rather than a silent default. A retry or repair is a separate generation stage and needs its own count and evaluation. The native constrained run is not a repair workflow: its grammar restricts generation itself. Both approaches still need semantic checks before an application trusts the content.

## Worked example

For a request for three urgent pens, `{"item":"pen","quantity":8,"priority":"urgent"}` is valid and wrong. Quantity true is rejected even though Python booleans are integer subclasses. Two quantity keys are rejected instead of silently accepting the last one. Try these inputs and inspect the separate contract and correctness indicators.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-output-verification:start */}

```python
import json

raw = '{"item":"pen","quantity":8,"priority":"urgent"}'
value = json.loads(raw)
valid = (
    set(value) == {"item", "quantity", "priority"} and type(value["quantity"]) is int
)
expected = {"item": "pen", "quantity": 3, "priority": "urgent"}
print("basic shape:", valid, "content correct:", value == expected)
```

## When to use it

Use explicit verification whenever generated text becomes structured application data, a calculation, or a user-facing claim. Choose validators tied to the task instead of treating fluency or another uncalibrated model judgment as sufficient.

## Limits and common mistakes

Validation cannot recover missing ground truth. A schema cannot establish factual support. The short snippet illustrates two layers only; the connected source implements the complete strict contract and negative tests.
