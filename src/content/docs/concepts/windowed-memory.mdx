## Definition and intuition

Windowed memory retains a recent slice of a conversation, usually defined in messages, turns, or tokens. The unit and later budget-packing rule must be explicit because they determine which earlier facts disappear.

A recent window is predictable and inexpensive to maintain. It can also forget the only occurrence of a project code while keeping several irrelevant recent messages. Recency is a policy choice, not a relevance guarantee.

## How it works

### The exact window

L11 selects the last two complete user/assistant pairs from the same eight-message conversation used by all policies. This is four messages, not two messages and not a fixed token count. The runtime then assembles system instructions and the final question and checks the actual rendered input against the application budget plus reserved output.

### Two removal stages

Messages outside the selected window are policy omissions. If the selected window is still too large, oldest complete pairs are budget evictions. The display lists both categories. This distinction matters when debugging why a fact disappeared: widening the window cannot help if a smaller budget immediately evicts the same material.

### Current framework equivalent

The workflow uses MessagesPlaceholder with a normal list of typed HumanMessage and AIMessage objects in pinned langchain_core. It verifies the same prompt and greedy output as the plain-Python window policy. It avoids deprecated memory classes and makes the selection rule explicit instead of depending on a historical convenience class’s interpretation of k.

## Worked example

The last two pairs contain the Monday correction and paint discussion, while the initial LARK-27 code is outside the window. A model may answer Monday from the retained text while missing the code. That is a predictable information boundary. The actual generated answer and field scores show whether the model uses the available material.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-windowed-memory:start */}

```python
history = [("u1", "a1"), ("u2", "a2"), ("u3", "a3"), ("u4", "a4")]
k = 2
kept = history[-k:]
omitted = history[:-k]
print("kept pairs:", kept)
print("policy omissions:", omitted)
assert len(kept) == 2
```

{/* example:e5-windowed-memory:end */}


## When to use it

Use a recent window when tasks mainly depend on nearby turns and predictable context size matters. Test an early unique fact, a later correction, and irrelevant recent chatter before assuming the policy fits your conversation.

## Limits and common mistakes

The window can forget old but essential facts. A message-count window does not impose a token cap, so token packing remains necessary. This lab does not add retrieval to rescue forgotten facts.

## Check your understanding

<details>
<summary>Does k=2 always mean two messages?</summary>

No. Here it explicitly means two complete user/assistant pairs. Different APIs can choose different units.

</details>

<details>
<summary>Does a wider window guarantee the early code reaches the model?</summary>

No. A later token-budget packing step may still evict the oldest pairs.
