## Definition and intuition

**Chains**: A chain links several operations so one step's output becomes another step's input.

Chapter 7 combines model calls with templates, memory, and tools. Trace the inputs and outputs of each step so an error can be located rather than hidden inside a chain.

## Before you start

Read [Prompt templates](/llm-concept-atlas/concepts/prompt-templates/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **Chains** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Define each operation's input and output contract
2. **Transform:** Pass data between retrieval, formatting, model, or parsing stages
3. **Inspect:** Log and evaluate intermediate results.

### The important distinction

Each chain stage should have an explicit input type, output type, and failure behavior. That turns a multi-call process into a system that can be measured. A chain is not automatically an agent: the sequence can be fixed, while an agent selects its next action based on observations.

## Worked example

A question enters retrieval, then a prompt builder, then a generator, then a validator. If the final answer is wrong, inspect the retrieved passage before changing the generator. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
def retrieve(question): return "Library closes at 5 pm Saturday."
def format_prompt(question, source): return f"Question: {question}\nSource: {source}"
question = "When does the library close?"
print(format_prompt(question, retrieve(question)))
```

**Expected output:**

```text
Question: When does the library close?
Source: Library closes at 5 pm Saturday.
```

**What the code shows:** The output of `retrieve` becomes an argument to `format_prompt`. Replace that returned passage with irrelevant text to see why downstream fluency cannot fix retrieval. The [official chapter 7 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter07) develops the corresponding model-based implementation.

## When to use it

Use chains for repeatable multi-step workflows where intermediate outputs have meaning. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- Long chains add latency and can hide error propagation if stages are opaque.
- **Failure to look for:** The retrieval stage returns no source but the generation stage still produces a fluent answer.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
