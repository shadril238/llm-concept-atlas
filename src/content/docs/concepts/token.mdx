## Definition and intuition

A token is one unit from a tokenizer’s vocabulary at a particular sequence position. It may represent a word, part of a word, punctuation, a byte-related piece, or a special task marker.

A reader counts five words and assumes the model uses five positions. A rare word, emoji, or boundary marker can change that count, so a word-based budget can overflow even on a short passage.

## How it works

A token string is the tokenizer’s readable notation for a vocabulary entry; a token ID is the integer supplied to the model. The ID selects an embedding row. Its magnitude does not measure importance, frequency, or semantic closeness.

A token occurrence has a position in the sequence. Two occurrences can share an ID while receiving different contextual states later. Conversely, one visible character can require several byte-based tokens. Always distinguish vocabulary identity, occurrence position, and later representation.

Special tokens can indicate boundaries, padding, unknown input, masking, or roles. Their behavior is tokenizer/model-specific. A visible string that resembles a special marker is not necessarily encoded as that marker under every tokenizer configuration.

### The important distinction

Joining piece strings manually can mishandle whitespace and byte fragments.

## When to use it

Count tokens with the actual paired tokenizer after adding templates and markers. Use character/word counts only as estimates. When building an annotation task, retain a mapping to original words or character offsets so output positions can be interpreted.

## Limits and common mistakes

Joining piece strings manually can mishandle whitespace and byte fragments. Decoding one token at a time may display incomplete characters. A token count measures an encoding, not a model’s language competence or correctness.
