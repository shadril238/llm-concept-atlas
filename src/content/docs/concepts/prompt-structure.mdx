## Definition and intuition

A prompt is the model input assembled from roles, instructions, task data, demonstrations, and output requirements. A chat model also expects a particular serialization of role boundaries; the visible text alone is not the whole input.

A prompt can be concise and precise or long and contradictory. Adding more components is not automatically an improvement. The useful question is which change affects a defined task under a fixed model and generation configuration.

## How it works

### Prompt ingredients

The instruction states the requested action; context supplies relevant background; task data is what must be processed; examples demonstrate input/output behavior; the output contract defines what a downstream program may accept. A role such as system or user is serialized into special delimiters for the chosen chat model. Putting the words “system instruction” inside ordinary data does not create a genuine system boundary.

### Generation model selection

Start with task language, expected input/output length, hardware, artifact license, supported decoding controls, and representative validation cases. A base model and an instruction-tuned chat model may need different input conventions. E5 uses a small pinned Q8 GGUF instruction model to make CPU execution accessible. Its failures are displayed; size and quantization do not establish adequate task quality. No current-best-model recommendation is inferred from this tiny suite.

### Inspect the assembled input

The runtime exposes each typed message, its serialized ChatML text, exact native input-token count, output cap, stop reason, and generated text. It verifies the renderer against the template stored in the GGUF artifact. Named fields and role boundaries are inspected before generation so formatting errors are distinguishable from model errors. The adapter rejects literal role delimiters inside this lab’s content; broader production input handling requires its own contract.

### Generation controls

Temperature changes sampling probabilities when it is positive; smaller values concentrate mass and larger values flatten it. This runtime treats temperature zero as greedy decoding, not a division by zero in a softmax formula. Top-k limits candidates by rank; top-p keeps a probability-mass nucleus under the backend's sampler order. These affect selection, not the truth of the selected token. A fixed seed helps reproduce a configuration but does not guarantee identical output across devices or native-library versions.

`max_tokens` caps generated output; stop sequences terminate at declared role boundaries. Both can end a response before it satisfies the requested contract, so inspect the finish reason and parse the complete output. The prompt plus reserved output must fit the context cap. L09 holds its greedy settings fixed across prompt comparisons; L10 separately records temperature 0.7, top-p 0.9, top-k 40, and five seeds. Those are different experimental questions. The [decoding lesson](/llm-concept-atlas/concepts/decoding/) develops the distribution calculation.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-prompt-structure:start */}

```python
parts = {
    "instruction": "Add the two counts.",
    "data": "7 books and 8 books",
    "format": "Return one integer only.",
}
for role, text in [
    ("system", parts["format"]),
    ("user", parts["instruction"] + " Data: " + parts["data"]),
]:
    print(role + ":", text)
assert "7" not in parts["format"]  # task data is separate from the contract
```

{/* example:e5-prompt-structure:end */}

Expected mechanism output:

```text
system: Return one integer only.
user: Add the two counts. Data: 7 books and 8 books
```

## When to use it

Use an explicit prompt assembly layer whenever a model is part of a program. Preserve versions and rendered inputs so changes can be reviewed and evaluated rather than judged by one pleasing answer.

## Limits and common mistakes

A correct template does not guarantee an answer. Prompt tokens consume context capacity alongside reserved output. E5 uses original tasks and a small model; its measured results are not a general ranking of model families.

## Check your understanding

<details>
<summary>Is a task paragraph beginning “system:” a system message?</summary>

No. Roles are structured by the application and the model-specific renderer. An ordinary string that names a role does not create that boundary.

</details>

<details>
<summary>Why inspect the rendered prompt before comparing accuracy?</summary>

A role or delimiter mismatch can change the actual model input. Without inspecting it, a formatting bug can be mistaken for a model or prompting result.

</details>
