## Definition and intuition

Retrieval metrics measure whether a ranked list contains and prioritizes relevant items.

Chapter 8 separates finding evidence from using evidence. Evaluate retrieval and answer support independently because a fluent answer can still lack a trustworthy source.

## Before you start

Read [Semantic Search](/llm-concept-atlas/concepts/semantic-search/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **retrieval metrics** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Create queries with judged relevant passage IDs
2. **Transform:** Compute recall, precision, or rank-sensitive scores at a chosen cutoff
3. **Inspect:** Inspect failures by query type and corpus slice.

### The important distinction

Recall at k asks what fraction of all judged relevant items occur in the first k results. MRR rewards putting the first relevant result early, while nDCG can account for graded relevance and positions. Choose metrics that match how many passages the downstream user or model actually sees.

## Worked example

If two passages are relevant but only one appears in the top two, recall at two is one half. A high average can still hide poor results for rare questions. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
relevant = {"A", "C"}
ranking = ["B", "A", "C"]
k = 2
recall_at_k = len(relevant & set(ranking[:k])) / len(relevant)
print(recall_at_k)
```

**Expected output:**

```text
0.5
```

**What the code shows:** The numerator counts relevant IDs in the first `k` results; the denominator counts all judged relevant IDs. Changing `k` changes what the metric asks. The [official chapter 8 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter08) develops the corresponding model-based implementation.

## Limits and common mistakes

- Metrics depend on relevance judgments and the cutoff, and they do not prove answer quality.
- **Failure to look for:** A system scores well at recall@20 but the generator sees only the top three passages.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
