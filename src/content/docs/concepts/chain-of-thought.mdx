## Definition and intuition

Chain-of-thought prompting asks for intermediate reasoning text before an answer. That visible text is a generated explanation, not a faithful readout of hidden computation or a guarantee of correctness.

A useful worked solution exposes checkable operations. An impressive explanation can also rationalize a wrong result. The aim is to make claims testable, not to assume that more words imply better reasoning.

## How it works

### Within one generation

A model predicts output tokens conditioned on its input and earlier generated tokens. Asking it to write intermediate steps changes that continuation. It does not create separate application calls, a search tree, or an external arithmetic verifier. Visible reasoning can contain arithmetic mistakes, omitted assumptions, or a correct answer supported by an incorrect explanation.

### Two prompt families

The book discusses worked demonstrations and a zero-shot step-by-step instruction. L09 keeps these distinct: step-instruction has no demonstration, while worked-example includes a design-split calculation and Answer line. Both use the same evaluation questions. The comparison reports answer extraction, format following, and actual token work rather than assuming either instruction improves results.

### What can be inspected

The displayed text is an observable output artifact. It is not evidence that every internal operation followed the narrative. Check intermediate arithmetic when it is relevant, and separately check the final reference answer. For a production workflow, concise justifications, executable calculations, or cited evidence can provide more useful verification targets than an unrestricted narrative.

## Worked example

For seven plus eight, “7 + 8 = 14; Answer: 14” has a clear structure and a wrong calculation. “Answer: 15” is correct under the answer-line parser but supplies no checkable intermediate reasoning. L09 retains both format and answer metrics. Its tiny model often fails to produce an extractable final line; those failures are not silently discarded.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-chain-of-thought:start */}

```python
steps = [(7, 8, 14), (7, 8, 15)]
for left, right, claimed in steps:
    print(f"{left} + {right} = {claimed}", "verified:", left + right == claimed)
assert 7 + 8 == 15
```

{/* example:e5-chain-of-thought:end */}


## When to use it

Use short worked demonstrations when task decomposition is understandable and its intermediate claims can be checked. Compare against a direct-answer baseline and account for the added output budget and work.

## Limits and common mistakes

Longer output may add unsupported steps or hit the token cap. An explanation is not privileged access to internal reasoning. The recorded local results support only this task/model configuration and do not establish a general advantage for visible reasoning.

## Check your understanding

<details>
<summary>Is a written explanation an internal execution trace?</summary>

No. It is generated text. External checks can assess its claims, but the text does not reveal every hidden model operation.

</details>

<details>
<summary>Does “think step by step” implement tree search?</summary>

No. Tree search requires explicit candidate states, branching, evaluation, pruning, and stopping logic in the application.
