## The idea in plain language

You are building a document assistant. A 500-word passage fits one model and overflows another. Why? Models budget their input in **tokens**, and different tokenizers can turn the same text into different-length sequences.

**Tokenization** is the conversion of text into an ordered sequence of vocabulary items and their integer IDs, using a particular tokenizer's rules. A tokenizer is part of a model's input contract. It does not infer a word's contextual meaning; the model's embedding and transformer layers perform later numerical processing. Think of the tokenizer as an agreed encoding system: both sender and receiver must use the same vocabulary. The analogy stops at meaning—an ID is an address, not a definition.

## See a worked example

Start with `Language models learn patterns.`. Predict whether punctuation becomes a separate piece, whether capitalization survives decoding, and whether boundary markers add to the count. Then inspect both tokenizers below.

<TokenizerExplorer client:visible />

The piece buttons display **actual recorded IDs**. Selecting one exposes its original-string offsets. Offsets are half-open character ranges: `[0, 8)` covers positions 0 through 7. Added special tokens can have an empty source range. A Unicode character can occupy several UTF-8 bytes, so byte-based pieces may share a character's offset range. Offsets are not a universal one-to-one map between pieces and characters.

For the English example, BERT's uncased normalization removes capitalization. Its vocabulary lookup adds `[CLS]` and `[SEP]` under the default single-sequence encoding. GPT-2's byte-BPE encoding does not add those BERT markers. Look at the recorded count rather than assuming two tokenizers must agree.

### Try changing the split

Choose **Unusual word** and compare `unbelievableness`. WordPiece marks internal continuations with `##`; GPT-2 uses visible byte notation, including a symbol often rendered as `Ġ` for a leading space. These symbols describe vocabulary entries; they are not decorations to append to your input. Decode the complete ID sequence with the tokenizer instead of manually joining the displayed pieces.

Next select **Korean + emoji**. BERT's English uncased vocabulary can lose information through normalization and unknown tokens. GPT-2's byte vocabulary can represent the supplied text and reconstruct it, although it may use many pieces. This does not establish that GPT-2's language model understands Korean well. Representability, compression, and downstream model quality are separate properties.

Finally select **Python + whitespace**. Inspect the newline, indentation, quotes, and punctuation. Removing whitespace to reduce a token count can change a program's meaning. The compactness of an encoding is useful only if it preserves information your task needs.

## How tokenization works

A trained tokenizer commonly combines the following operations; the exact pipeline is model-specific.

| Stage | Input → output | What to inspect |
| --- | --- | --- |
| Normalization | Original Unicode text → normalized text | Case folding, accents, and whitespace policies can discard distinctions. |
| Pre-tokenization | Normalized text → candidate spans | Spaces and punctuation often guide boundaries. This stage differs across tokenizers. |
| Subword segmentation | Spans → vocabulary pieces | The algorithm selects known units; unusual text may need many pieces. |
| ID lookup | Pieces → integers | IDs must match the paired model's embedding rows. |
| Post-processing | IDs → model-ready sequence | Add task markers, attention masks, padding, or other fields when needed. |

**Training a tokenizer** learns a vocabulary and segmentation rules from a corpus. **Encoding text** applies a fixed tokenizer to a new input. These are different jobs. The pretrained comparison performs encoding; it does not train either tokenizer or either language model.

### Why not split on spaces?

Space splitting cannot consistently handle punctuation, languages without word spaces, unfamiliar compounds, emoji, and source-code layout. A whole-word vocabulary also needs a policy for words absent from training. Character tokenization avoids many unknown-word problems but lengthens the input; byte tokenization covers encodable text using byte units and can require multiple pieces per visible character.

**BPE (byte pair encoding)** begins with smaller units and learns merges of frequently adjacent pairs. A toy sequence `l o w` might become `lo w`, then `low`, if those merges were learned. The merge rules and order determine encoding; you cannot infer the full vocabulary from this toy trace. **WordPiece** also uses subword units, with its own vocabulary learning and matching procedure. **Unigram** starts from a candidate vocabulary and uses a probabilistic segmentation model. SentencePiece is a toolkit that can implement BPE or Unigram; it is not a synonym for a third universal segmentation algorithm.

A useful accounting equation is `total input length = content pieces + inserted special tokens + prompt/template tokens`. Padding extends a batch tensor, but its mask distinguishes those filler positions from actual content. An attention mask of 0 marks padding for these examples; a training label of −100 has a different role, which the NER lesson explains.

### Special tokens and context budgets

BERT's `[CLS]`, `[SEP]`, `[PAD]`, `[UNK]`, and `[MASK]` have task-specific uses. GPT-2 has a different special-token scheme. Setting `add_special_tokens=False` is an experiment, not a safe default for every task. Chat models may additionally require a template with role and turn markers. Count the **final encoded prompt**, including its template, before reserving room for generated output.

The same integer can refer to unrelated pieces in two vocabularies. Even if two tokenizers report the same vocabulary size, swapping them can silently feed the wrong embedding rows into a model. Loading succeeds is a weaker test than checking the model/tokenizer identity and revision.

{/* example:tokenizer-comparison:start */}

```python
"""Compare two actual tokenizer vocabularies and normalization policies."""

import json
from pathlib import Path
from transformers import AutoTokenizer

ROOT = Path(__file__).resolve().parents[5]
SPECS = [
    ("google-bert/bert-base-uncased", "86b5e0934494bd15c9632b12f734a8a67f723594"),
    ("openai-community/gpt2", "607a30d783dfa663caf39e06633721c8d4cfcd7e"),
]
TEXTS = [
    "Language models learn patterns.",
    "unbelievableness",
    "안녕하세요 👋",
    'print("Hello")\n  x = 2',
]


def main():
    examples = []
    for model_id, revision in SPECS:
        tokenizer = AutoTokenizer.from_pretrained(
            model_id, revision=revision, use_fast=True
        )
        for text in TEXTS:
            encoded = tokenizer(
                text, return_offsets_mapping=True, return_special_tokens_mask=True
            )
            ids = encoded["input_ids"]
            examples.append(
                {
                    "model": model_id,
                    "text": text,
                    "pieces": tokenizer.convert_ids_to_tokens(ids),
                    "ids": ids,
                    "offsets": encoded["offset_mapping"],
                    "special": encoded["special_tokens_mask"],
                    "decoded": tokenizer.decode(
                        ids,
                        skip_special_tokens=True,
                        clean_up_tokenization_spaces=False,
                    ),
                }
            )
            assert (
                len(ids)
                == len(encoded["offset_mapping"])
                == len(encoded["special_tokens_mask"])
            )
            if "gpt2" in model_id:
                assert tokenizer.decode(ids, clean_up_tokenization_spaces=False) == text
        # Empty input is still a valid encoded input; BERT adds two markers.
        assert len(tokenizer("")["input_ids"]) == (2 if "bert" in model_id else 0)
    path = ROOT / "examples/artifacts/tokenizers"
    path.mkdir(parents=True, exist_ok=True)
    (path / "results.json").write_text(
        json.dumps(examples, indent=2, ensure_ascii=False) + "\n"
    )
    print(
        json.dumps(
            {
                "tokenizers": 2,
                "cases": len(examples),
                "roundtrip_gpt2": True,
                "counts": [len(row["ids"]) for row in examples],
            }
        )
    )


# region usage
if __name__ == "__main__":
    main()
# endregion usage
```

`use_fast=True` enables the alignment information used here. `return_offsets_mapping` ties pieces to source characters; `return_special_tokens_mask` identifies added markers. The script checks matching array lengths, empty-input behavior, and exact GPT-2 round trips for these fixtures. BERT's output is allowed to differ from the original because its normalization intentionally changes text. Assertions should test the tokenizer's documented contract, not demand impossible lossless decoding from an uncased tokenizer.

Inspect `examples/artifacts/tokenizers/results.json` after running. Changing a string requires rerunning the tokenizer; the browser does not fabricate new pieces. The locked environment and pinned revisions let another reader inspect the same vocabulary. Later library changes still require re-verification.

## Why it matters

- **Retrieval:** chunk source documents with the target tokenizer and leave room for the question, instructions, and answer. A character count is an estimate, not the final budget.
- **Multilingual products:** compare counts and information loss on the actual scripts your users write. An English-only fixture cannot establish multilingual suitability.
- **Training:** align word-level annotations with actual model pieces. The [NER lesson](/llm-concept-atlas/concepts/named-entity-recognition/) makes that mapping explicit.
- **Cost and latency:** input length affects many workloads, but the cheapest encoding is not automatically the most accurate model.

## Limits and common mistakes

A token is not always a word, an ID is not a semantic score, and individual-token decoding need not reconstruct every character cleanly. Do not equate byte coverage with language competence or assume a token-count comparison ranks language models. Truncation can cut an instruction or entity in half. Inspect the retained content and choose a task-aware policy rather than silently accepting the first N tokens.
