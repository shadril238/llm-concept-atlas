## Definition and intuition

**Reward models**: A reward model predicts a scalar preference or quality score from a prompt-response pair.

Chapter 12 distinguishes pretraining, instruction tuning, and preference optimization. Efficient adapters change a subset of parameters; evaluation still decides whether behavior improved.

## Before you start

Read [Generative evaluation](/llm-concept-atlas/concepts/generative-evaluation/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **reward models** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Collect comparisons or rated examples with clear criteria
2. **Transform:** Train a scorer to rank preferred responses above rejected ones
3. **Inspect:** Validate on new prompts and watch for exploitation by a policy model.

### The important distinction

A reward model often learns from pairwise preferences by assigning a higher scalar score to the chosen response. This score is a proxy for a rubric, not a direct measurement of truth. Evaluate whether a generator can exploit the proxy through verbosity, style, or hidden shortcuts.

## Worked example

Reviewers prefer an accurate short answer over a longer invented one. The reward model learns that preference signal, but a policy may later find ways to earn score without being useful. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
from math import log, exp
chosen_logprob, rejected_logprob = -0.4, -1.1
reference_gap = 0.2
beta = 0.5
gap = beta * ((chosen_logprob - rejected_logprob) - reference_gap)
loss = log(1 + exp(-gap))
print(round(loss, 3))
```

**Expected output:**

```text
0.576
```

**What the code shows:** The loss compares the policy preference gap with a reference gap, scales it by beta, and applies a logistic penalty. A lower toy loss does not validate the preference labels. The [official chapter 12 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter12) develops the corresponding model-based implementation.

## When to use it

Use one as a learned proxy for human preferences in alignment workflows. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- Its score reflects training preferences and can be gamed; it is not a universal truth measure.
- **Failure to look for:** A verbose answer earns high reward because length correlated with preferred examples.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
