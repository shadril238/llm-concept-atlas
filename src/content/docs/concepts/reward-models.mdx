## Definition and intuition

A reward model maps a prompt and one candidate completion to a scalar score. Pairwise preference training learns to rank a preferred completion above a rejected one for the same prompt. The score is a learned relative signal, not a calibrated probability that the response is true.

## Before you start

Read [pretraining and sft](/llm-concept-atlas/concepts/pretraining-and-sft/). Distinguish a token distribution, a trainable parameter, and a task score before tracing this mechanism.

## Theory: how it works

### Inputs and scalar outputs

A sequence scorer jointly encodes prompt plus candidate and applies a scalar head. Chosen and rejected answers share the prompt but require two candidate evaluations. L23 uses a tiny pretrained BERT encoder with a newly initialized one-output classification head; the base language model is not reused as a fake scalar reward head. Every parameter of this small reward model is optimized.

For reward values rc and rr, the Bradley–Terry preference probability is sigmoid(rc−rr). Pairwise loss is −log(sigmoid(rc−rr)), evaluated stably using log-sigmoid. Adding a common constant to both scores does not change the probability, so absolute reward offsets are unidentified by this objective. A pairwise score of 3 is not “three units of correctness” and cannot be compared across arbitrary separately trained reward models.

### Preference pair construction

Each example preserves prompt, chosen, rejected, split and label provenance. Both candidates can be wrong; “chosen” means preferred under a stated criterion. Identical or empty candidates are invalid here. Avoid placing the answer outside a truncated window or comparing candidates under different prompts. L23 rejects overflow instead of silently cutting one candidate differently.

Our preference fixture derives from the fixed Dolly extraction subset. The original reference is preferred over a rule-authored unsupported abstention, irrelevant addition, swapped answer or unwarranted refusal. These are transparent pedagogical labels, not independent human annotations or on-policy samples. Eight heldout contexts remain unseen during fitting and checkpoint selection. Some defects are easy shortcuts; we report a shorter-answer baseline, lengths and per-error-type rows to make that limitation visible.

### The important distinction

Reward training uses scalar rewards produced by the reward model. It does not use policy/reference token log probabilities or a DPO beta. L23 contains both algorithms in separate code paths so this difference is inspectable. The reward model is saved/reloaded and evaluated on heldout pair ranking; it is deliberately not consulted during DPO. In PPO-style RLHF it could become a reward signal, but that policy optimization is conceptual here, not secretly executed.

## Worked example

With chosen reward 1.2 and rejected reward 0.4, the margin is 0.8, sigmoid probability about 0.69 and pair loss about 0.371. Raising both rewards by 100 gives the same probability and loss. Reversing their order gives a larger loss. The code below performs only that scalar calculation; L23 performs actual encoder/head optimization.

Before and after training, inspect heldout accuracy, ties, individual margins and candidate lengths. If the trained model prefers every longer answer, high aggregate accuracy on a length-biased fixture is weak evidence. A separate slice with short correct and long incorrect candidates helps reveal that shortcut.

## Implement it

This standalone Python 3 calculation uses only the standard library. It does not download or train a model. The [complete generation labs](/llm-concept-atlas/labs/generation-adaptation/) provide the pinned environments, actual training entrypoints, staged notebooks, raw results and artifact checks.

{/* example:e8-reward-models:start */}

```python
from math import exp, log1p

chosen, rejected = 1.2, 0.4
margin = chosen - rejected
probability = 1 / (1 + exp(-margin))
loss = max(0, -margin) + log1p(exp(-abs(margin)))
print("preference probability:", round(probability, 4))
print("reward ranking loss:", round(loss, 4))
assert abs(((chosen + 100) - (rejected + 100)) - margin) < 1e-12
print("Common score offsets do not change a pairwise preference.")
```

## When to use it

Reward models can support candidate reranking or provide a policy-training signal when the preference rubric is clear and labels represent intended users. They can learn annotator biases, verbosity shortcuts or unsupported confidence. Treat reward improvement as a hypothesis about task quality that needs independent heldout and human checks.

## Limits and common mistakes

The evaluated instruction subset has 32 training,8 validation and 8 test source contexts. Pretraining overlap is unknown. Repeated views of these test outputs are not a new independent benchmark. Preserve failed and length-limited answers, exact base/tokenizer identity and data provenance when transferring the workflow. The book's larger TinyLlama/CUDA settings require their own supported hardware execution; the small profiles do not certify them.

## Check your understanding

<details>
<summary>Why is reward 3 not an absolute factuality guarantee?</summary>

The objective constrains relative margins under its training preferences. A common offset is unconstrained, and the labels/model may reward shortcuts unrelated to factuality.

</details>

<details>
<summary>Which actual model supplies the DPO loss in L23: the reward model or policy/reference?</summary>

Policy and frozen-reference completion log probabilities supply DPO. The separately trained scalar reward model is evaluated and saved but never queried by that training loop.

</details>
