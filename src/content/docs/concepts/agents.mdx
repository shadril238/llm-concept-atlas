## Definition and intuition

**Agents**: An agent is a model-directed system that chooses actions or tools in a loop to reach a goal.

Chapter 7 combines model calls with templates, memory, and tools. Trace the inputs and outputs of each step so an error can be located rather than hidden inside a chain.

## Before you start

Read [Chains](/llm-concept-atlas/concepts/chains/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **Agents** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Define the goal, available tools, and stop conditions
2. **Transform:** Select an action, execute it, and observe the result
3. **Inspect:** Repeat with limits and validate the final outcome.

### The important distinction

The model proposes actions, while application code decides which tools exist and enforces limits. A useful agent trace records tool inputs, outputs, and stop reasons. Reserve user approval for consequential external actions; a successful-looking plan is not evidence that the action completed.

## Worked example

A travel assistant looks up train times, compares routes, and drafts an itinerary. Each tool result is evidence to inspect; the model's plan alone is not a booking. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. ## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
tools = {"lookup": lambda item: {"hours": "5 pm"}.get(item, "unknown")}
plan = [("lookup", "hours")]
for tool, argument in plan:
    print(tool, argument, "->", tools[tool](argument))
```

**Expected output:**

```text
lookup hours -> 5 pm
```

**What the code shows:** The code executes a named tool with an argument and records its observation. A real agent chooses actions dynamically, but application code must still enforce the tool boundary. The [official chapter 7 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter07) develops the corresponding model-based implementation.

## Limits and common mistakes

- Tool calls can have side effects, so permissions, logs, and bounded loops matter.
- **Failure to look for:** The agent claims a reservation was made after only reading a timetable.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
