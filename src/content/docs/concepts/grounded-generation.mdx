## Definition and intuition

Grounded generation asks a model to answer from supplied evidence and ties its claims to inspectable sources. Correct wording, source-ID resolution, and genuine evidential support are distinct checks.

Read this lesson as a sequence: identify the input, follow the transformation, inspect the result, and explain a failure. The worked example and recorded lab below make those boundaries visible.

## How it works

### Pack actual evidence with provenance

L13 preserves chunk and document IDs, source offsets, the original question, and every passage actually included in the prompt. Whole passages fit a 384-token application input budget under a 512-token native cap. Duplicate document chunks and passages that do not fit are explicitly omitted. The system does not silently insert gold support passages after retrieval.

### Citations need a semantic check

A model can emit a valid source ID without answering, cite a selected passage that does not support its statement, or give a correct short answer without any citation. The parser records actual markers and rejects unknown IDs as unresolved; it never attaches references and calls them model citations. Author proposition review separately checks correctness, context faithfulness, utility, fluency, and citation support, retaining uncertainty.

### API grounded generation

The optional hosted route is a documented workflow plus an actual offline importer, consistent with the project preference. It accepts provider/model/prompt/time provenance, known query IDs, source IDs, answer spans, source spans, and exact quotes. Offsets are Unicode code points. Resolving those objects checks provenance and span integrity, not entailment. No paid API call, hosted quality score, or live-provider execution is claimed.

## Worked example

The number 57 appears in the Aspen contact passage. It does not support “the team maintaining Wren is at 57,” because Wren belongs to Birch, whose extension is 42. ## Implement it

From the repository root, run `python3 scripts/run-examples.py --id e6-grounded-generation --offline` after installing the foundation environment. This standard-library example calculates the stated mechanism or replays hash-linked actual model evidence from the published snapshot. It does not perform a fresh neural-model inference. The complete local/CI implementation and execution contract are linked immediately below.

{/* example:e6-grounded-generation:start */}

```python
import json
from pathlib import Path
data = json.loads(Path('src/data/retrieval-results.json').read_text())
row = next(r for r in data['grounded']['rows'] if r['id']=='eval-hop' and r['variant']=='baseline')
print('raw answer:',row['answer_call']['raw'])
for source in row['context']:
    if source['document_id'] in ['wren','birch','aspen']:
        print(source['id'],source['text'])
print('Reference answer is evaluation-only:',row['reference_answer'])
```

## When to use it

Use grounded drafting for document-based explanations where a reader must inspect the evidence for each material claim. Preserve the exact context and distinguish a model-provided citation from an application-provided source pointer.

## Limits and common mistakes

An exact quote may be irrelevant to its attached claim. A fluent answer can be unsupported, and a correct answer can be uncited. Provider citation objects and local bracket markers require their own format checks; neither establishes semantic truth automatically.

## Check your understanding

<details>
<summary>Does a source span matching its quote prove entailment?</summary>

No. It proves where the quoted text occurs. A human or carefully qualified support evaluator must still relate it to the claim.

</details>

<details>
<summary>Should application-selected source pointers be reported as model citations?</summary>

No. Keep retrieved sources, emitted citation markers, and judged claim support separate.

</details>
