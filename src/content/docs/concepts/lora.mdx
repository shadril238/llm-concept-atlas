## Definition and intuition

Suppose a pretrained language model almost performs your task, but updating and storing every weight for every task is too expensive. **Low-Rank Adaptation (LoRA)** freezes selected pretrained weight matrices and learns a small, factorized additive update. The original matrix remains in the forward pass. LoRA does not replace the base model with two tiny matrices.

Imagine learning a small correction to a map instead of redrawing the entire map. The correction still depends on the original map. This analogy explains the storage relationship; it does not prove a low-rank correction can represent every change your task requires.

## Before you start

A weight matrix is a learned linear transformation. **Rank** is the number of independent directions a matrix can express. A product of two matrices with an inner dimension r has rank at most r. **Fine-tuning** changes parameters using task data; **inference** computes outputs using the current parameters. A frozen parameter participates in the forward computation but is excluded from optimizer updates.

The small adapter reduces trainable parameters and their optimizer state. Activations, the frozen base weights, and computation through the network still consume memory. LoRA alone does not make a large model fit every CPU or GPU. [QLoRA](/llm-concept-atlas/concepts/qlora/) additionally quantizes base weights; the full-precision CPU workflow here does not verify that different configuration.

## Theory: how it works

Fix the orientation first. Use column vectors in the explanation:

| Symbol | Shape | Role |
| --- | --- | --- |
| x | d_in × 1 | Input activation |
| W | d_out × d_in | Frozen pretrained weight |
| A | r × d_in | Trainable projection into r directions |
| B | d_out × r | Trainable projection back to output width |
| α | Scalar | Adapter scaling hyperparameter |

The standard LoRA update used here is `ΔW = (α/r) B A`. The output is `y = W x + (α/r) B(Ax)`. First A compresses the input, then B expands the result, then the scaled correction is added to the original output. The factorized update is constrained; the rank of **W + ΔW** can still be high because W is retained.

PyTorch commonly batches row vectors. The same computation becomes `X @ W.T + (α/r) * (X @ A.T) @ B.T`. A transpose changes notation, not the underlying transformation. Some variants use different scaling, such as α divided by the square root of rank. Read the configuration before comparing experiments.

The adapter has `r × (d_in + d_out)` parameters, compared with `d_in × d_out` base weights. For a 4096 × 4096 projection at r = 8, that is 65,536 trainable adapter values versus 16,777,216 frozen values: about 0.39%. This is a parameter count, not a prediction of total training-memory reduction.

### The important distinction

LoRA constrains the **update**, not an arbitrary reconstruction of the complete pretrained weight. Lower rank reduces capacity and storage, but neither a small nor a large rank guarantees useful adaptation. Target-module choice, data coverage, learning rate, and evaluation matter. Adapting fused Q/K/V projections in Pythia is not the same module selection as adapting separate query/value projections in another architecture.

## Worked example

Let W be the 2 × 2 identity matrix, A = `[0.3, −0.1]`, B = `[0.1, 0.2]` as a column, x = `[2, 1]` as a column, and α = r = 1.

1. `Ax = 0.3×2 − 0.1×1 = 0.5`.
2. `B(Ax) = [0.05, 0.10]`.
3. `Wx = [2, 1]`, so `y = [2.05, 1.10]`.

The corresponding update matrix is `[[0.03, −0.01], [0.06, −0.02]]`. Multiplying this matrix by x gives exactly the same correction. There are four adapter parameters and four base parameters in this deliberately tiny example, so it demonstrates the calculation without offering parameter savings.

## Implement it

### A complete arithmetic trace

Run `python3 scripts/run-examples.py --id lora-trace`. This standard-library example follows exactly the orientation above:

{/* example:lora-trace:start */}

```python
W = [[1.0, 0.0], [0.0, 1.0]]  # [d_out=2, d_in=2]
A = [[0.3, -0.1]]  # [r=1, d_in=2]
B = [[0.1], [0.2]]  # [d_out=2, r=1]
x = [2.0, 1.0]
alpha, rank = 1.0, 1
compressed = sum(a * value for a, value in zip(A[0], x))
update = [(alpha / rank) * row[0] * compressed for row in B]
output = [
    sum(w * value for w, value in zip(row, x)) + delta for row, delta in zip(W, update)
]
assert all(abs(a - b) < 1e-12 for a, b in zip(output, [2.05, 1.10]))
print("A @ x:", round(compressed, 2))
print("update:", [round(value, 2) for value in update])
print("output:", [round(value, 2) for value in output])
```

{/* example:lora-trace:end */}

### Make the update learn

```bash
uv sync --locked --project examples/training/reference
python3 scripts/run-examples.py --id lora-tiny-training
```

The tiny task learns a known rank-one correction to an 8 × 8 identity transformation from 48 synthetic training vectors and evaluates on 16 separately drawn vectors. The frozen base, a full 64-parameter update, and a 16-parameter adapter see the same target function. This is a controlled regression experiment with an exactly representable rank-one solution; it is intentionally easier than language adaptation.

With random A and zero B, the initial adapter output is zero. On the first backward pass, A's gradient is zero because its path is multiplied by B, while B can receive a nonzero gradient through A. After B moves, A can also learn. If **both** factors start at zero, neither receives a useful gradient through their product. The script checks first-step gradients, frozen W, test error, factorized/merged equivalence, and saved-adapter reload.

### Adapt a pretrained language model

```bash
python3 scripts/run-examples.py --id lora-pretrained --allow-network
# Cached rerun:
python3 scripts/run-examples.py --id lora-pretrained --offline
```

The supported model is `EleutherAI/pythia-14m`, pinned in the manifest. The authored task completes “animal” or “color” for a queried word. The split has 24 training prompts, four validation prompts, and four final test prompts with disjoint queried words. Shared phrasing makes this an instructional fixture, not a benchmark of real instruction following.

Here is the adapter configuration from the executable workflow. `base`, `torch`, and the imports are defined in the linked complete source; this excerpt belongs inside its `main()` function.

{/* example:lora-pretrained:start */}

```python
config = LoraConfig(
    task_type="CAUSAL_LM",
    r=4,
    lora_alpha=8,
    target_modules=["query_key_value"],
    lora_dropout=0.0,
    bias="none",
)
model = get_peft_model(base, config)
# Only the fused Q/K/V projections get adapters in this architecture.
optimizer = torch.optim.AdamW(
    [p for p in model.parameters() if p.requires_grad], lr=0.003
)
```

{/* example:lora-pretrained:end */}

The run uses rank 4, α = 8, zero dropout, learning rate 0.003, batches of four, and 40 steps on CPU. It masks prompt positions and padding with −100, leaving answer tokens and EOS in the causal-language-model loss. The model performs its next-token shift internally; do not shift labels a second time. The script checks that separate prompt encoding remains a prefix of the combined encoding, because subword merges can otherwise move a completion boundary.

Validation loss is checked at fixed intervals to select an adapter checkpoint. Final test loss compares the frozen pretrained model and the selected adapter on the same held-out prompts. The script hashes frozen parameters before and after training, reopens the saved adapter against the exact base revision, and compares reloaded and merged logits with floating-point tolerances. It also records a greedy completion so that readers can see behavior beyond a scalar loss.

## When to use it

LoRA is useful when multiple tasks can share the same base model, when adapter storage matters, or when optimizer-state memory limits full fine-tuning. Start with a baseline and a data-split policy. Select target layers using the architecture's actual module names, then compare task quality, runtime, and artifact size. A full update can be preferable when broad weight changes are needed and resources permit it; prompting or retrieval can be preferable when weights need not change at all.

## Limits and common mistakes

A low training loss can reflect memorization of templates. Rank is not a direct measure of “knowledge capacity.” Freezing weights does not remove their forward-pass cost. Adapter artifacts must be paired with the correct base revision; a shape-compatible different base is not interchangeable. Merge checks require evaluation mode and compatible precision. Quantized merging and GPU training need their own verified environments.
