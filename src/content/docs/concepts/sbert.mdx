## Definition and intuition

SBERT adapts transformer encoders to produce sentence embeddings that can be compared efficiently.

Chapter 10 trains representations by choosing which examples should be close or far apart. The construction of positive and negative pairs is part of the learning objective.

## Before you start

Read [Contrastive learning](/llm-concept-atlas/concepts/contrastive-learning/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **SBERT** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Encode each sentence independently through a shared encoder
2. **Transform:** Pool token states into one vector per sentence
3. **Inspect:** Train with similarity or contrastive supervision and compare vectors.

### The important distinction

SBERT-style models use a bi-encoder: each sentence gets one reusable vector. A common pooling choice averages token embeddings under an attention mask, though model-specific pooling varies. This architecture makes large-scale retrieval practical because documents can be embedded before a query arrives.

## Worked example

A thousand candidate sentences can be embedded once, then compared with a new query vector. A joint cross-encoder would need a separate forward pass for each pair. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
from math import sqrt
a, b = (0.8, 0.6), (0.7, 0.7)
dot = sum(x*y for x, y in zip(a, b))
cosine = dot / (sqrt(sum(x*x for x in a)) * sqrt(sum(y*y for y in b)))
print(round(cosine, 3))
```

**Expected output:**

```text
0.99
```

**What the code shows:** The code takes a dot product, divides by both vector lengths, and prints a cosine score. Change a coordinate to see how the direction changes the comparison. ## When to use it

Use it for scalable semantic search, clustering, or sentence similarity. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. ## Limits and common mistakes

- Bi-encoder efficiency trades away some pairwise interaction available to a reranker.
- **Failure to look for:** A semantically related sentence outranks one that actually answers the precise query.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
