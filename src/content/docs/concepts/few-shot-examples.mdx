## Definition and intuition

Few-shot prompting supplies a small set of input/output demonstrations. Their correctness, coverage, ordering, and token cost affect the resulting prompt, so counting examples alone does not describe the method.

One example can teach a format; two nearly identical examples can teach a brittle shortcut. Useful demonstrations make the intended mapping visible while leaving evaluation targets out of the input.

## How it works

### Correctness and coverage

A demonstration should match the same task and output contract as the query. Addition-only arithmetic examples do not cover subtraction, division, or multi-step reasoning. In L09, every example has a stable design ID and a reference answer. Deliberately limited coverage is documented so an attractive prompt is not mistaken for comprehensive instruction.

### Role and format consistency

Demonstrations are explicit user/assistant message pairs serialized through the verified ChatML renderer. Bare-integer conditions use integer demonstrations; the worked-example condition uses a short checkable calculation and an Answer line. Switching contracts between examples and query can create an avoidable conflict.

### Controlled comparison

The balanced pair and its reversed order have the same demonstration count and text but a different sequence. The addition-only pair changes content selection. Those are different interventions and are reported separately. Native prompt and output token counts show the actual work; a larger example count does not imply a predictable accuracy or latency change.

## Worked example

A balanced pair with answers 5 and 5 can still encourage a constant-answer shortcut. Inspect generated answers across all eight evaluation questions and ask whether they track the task or imitate the demonstrations. The original outputs remain available even when a condition achieves a low score.

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-few-shot-examples:start */}

```python
examples = [{"id": "design-add", "answer": 5}, {"id": "design-sub", "answer": 5}]
print("example IDs:", [row["id"] for row in examples])
print("distinct demonstrated answers:", len({row["answer"] for row in examples}))
print("reversed IDs:", [row["id"] for row in reversed(examples)])
```

## When to use it

Use a small, representative demonstration set to clarify labels, extraction conventions, or response shape. Choose and revise it using design/validation evidence, then evaluate on cases that were not used to construct the prompt.

## Limits and common mistakes

Small examples can be ambiguous, redundant, or too long. Correct demonstrations do not guarantee correct continuations. E5 measures one small model and task suite and does not establish a universal optimal number of examples.

## Check your understanding

<details>
<summary>Is two examples necessarily better than one?</summary>

No. Relevance, correctness, diversity, order, and token cost matter. Additional examples can reinforce a shortcut or crowd out useful context.

</details>

<details>
<summary>Why record example IDs in each model result?</summary>

They make contamination and prompt changes auditable. A reader can distinguish changed selection from changed ordering or generation settings.

</details>
