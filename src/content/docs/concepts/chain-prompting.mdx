## Definition and intuition

Chain prompting sends the actual output of one model call into a later prompt. It creates an explicit multi-call dataflow, which is different from requesting several written steps in one response.

A multi-step workflow can isolate smaller tasks, but it also creates new places for errors to propagate. A later model can fluently continue an earlier mistake unless the application checks the intermediate contract.

## How it works

### A concrete dataflow

L11 first generates a structured order extraction under a native schema. The application validates the object and computes a total from the extracted item/quantity and fixed unit prices. A second actual model prompt receives that generated object and calculated total, then produces a total object. Both calls, the intermediate state, and the reference order remain visible.

### Three correctness questions

Was the extraction correct for the original order? Was the arithmetic correct for the extracted order? Did the second call preserve the supplied total? These checks can disagree. A correct total for an incorrectly extracted quantity is still wrong for the user’s request. A second model call does not independently verify facts just because it comes later.

### Distinguish the vocabulary

A chain-of-thought-style prompt may generate a visible worked solution within one call. A chain is application dataflow across stages, which may include deterministic functions. A tree search branches across candidate states and uses an evaluator. These mechanisms can be combined, but their traces and costs are not interchangeable.

## Worked example

If a request asks for three pens at two units each, the reference total is six. If the first model extracts eight pens, a deterministic total of sixteen is internally correct for that extraction but wrong for the request. If the second model copies sixteen, copy consistency passes while end-to-end accuracy fails. L11 reports these checks separately.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-chain-prompting:start */}

```python
requested_quantity, extracted_quantity, price = 3, 8, 2
calculated = extracted_quantity * price
copied = calculated
print("arithmetic for extraction:", calculated)
print("copy consistent:", copied == calculated)
print("end-to-end correct:", copied == requested_quantity * price)
```

{/* example:e5-chain-prompting:end */}

Expected mechanism output:

```text
arithmetic for extraction: 16
copy consistent: True
end-to-end correct: False
```

## When to use it

Use multiple prompts when intermediate artifacts have clear roles and checks, or when stages need distinct instructions and output budgets. Preserve source IDs and stage inputs so a failure can be attributed rather than hidden in the final response.

## Limits and common mistakes

Every additional call adds work and another failure opportunity. Separating prompts is not proof of better answers. L11 retains its observed incorrect chain result and explains the stage at which it arose.

## Check your understanding

<details>
<summary>Does a correct second-stage copy prove the original extraction?</summary>

No. It only checks consistency with the supplied intermediate total. The original input/reference must be evaluated separately.

</details>

<details>
<summary>Is a paragraph with three numbered steps necessarily a three-call chain?</summary>

No. Call boundaries come from the application, not from the number of steps written in one generated response.

</details>
