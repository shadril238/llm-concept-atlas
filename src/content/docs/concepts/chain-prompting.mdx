## Definition and intuition

Chain prompting splits a difficult task into dependent, inspectable model calls or subprompts.

Chapter 6 treats a prompt as a task specification. A prompt can guide output, but it does not change model weights or guarantee that an answer is correct.

## Before you start

Read [Prompt structure](/llm-concept-atlas/concepts/prompt-structure/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **chain prompting** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Define a first subtask with a verifiable output
2. **Transform:** Pass that output into a second prompt with clear provenance
3. **Inspect:** Check each stage before accepting the final result.

### The important distinction

A chain can turn an uncheckable final answer into inspectable intermediate artifacts, such as retrieved passage IDs and a structured summary. Define contracts between stages so the next stage does not silently accept an empty or malformed result. The weakest upstream step often bounds final quality.

## Worked example

A research assistant first retrieves document IDs, then summarizes only those passages. If the first stage picked irrelevant documents, the final prose cannot repair missing evidence. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
def retrieve(question): return "Library closes at 5 pm Saturday."
def format_prompt(question, source): return f"Question: {question}\nSource: {source}"
question = "When does the library close?"
print(format_prompt(question, retrieve(question)))
```

**Expected output:**

```text
Question: When does the library close?
Source: Library closes at 5 pm Saturday.
```

**What the code shows:** The output of `retrieve` becomes an argument to `format_prompt`. Replace that returned passage with irrelevant text to see why downstream fluency cannot fix retrieval. The [official chapter 6 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter06) develops the corresponding model-based implementation.

## When to use it

Use it when intermediate results can be checked and reused. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- Each additional call adds latency and another failure point.
- **Failure to look for:** A mistaken intermediate fact is copied into later prompts and amplified into a confident conclusion.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
