## Definition and intuition

ReAct interleaves reasoning-oriented decisions with actions and returned observations. In an implemented workflow, the important evidence is the actual interaction between decisions, permitted tools, and their observations.

ReAct in this lesson refers to the reasoning-and-acting method, not the React frontend library used by the website. A written “Observation” supplied by a model is not automatically a genuine tool result.

## How it works

### The interaction loop

A controller assembles the task and prior observations, asks for a next action, validates it, runs the allowed tool, appends the actual result, and invokes the next decision. The trace preserves model outputs separately from resolved tool calls. When a tool rejects arguments, that validation error becomes an observation under the same bounded policy.

### A measured adaptation

The book’s broader ReAct discussion is adapted into a finite local action-ID workflow because the small GGUF model is unreliable at arbitrary tool-call text. It selects among pre-generated legal calls, then a final-value domain after observing a result. This is explicitly a restricted ReAct-style mechanism demonstration. No claim is made that it produced faithful hidden reasoning or a fully autonomous plan.

### Real and fake traces

L11 executes actual GGUF choices through plain-Python and LangChain tool paths. It also runs clearly labeled scripted/FakeListLLM cases that force invalid arguments and maximum-step exhaustion. The fake cases establish controller behavior under specified decisions, while the real cases show the weak model’s actual choices and errors. Current core Runnable and StructuredTool APIs replace historical agent-executor imports.

## Worked example

A lookup returns the fixture value 17:30 for library closing time. The next decision should use that observation. If the model instead selects another tool, the controller records the repetition and continues only within the three-step bound. If a fake test supplies a boolean calculator operand, strict validation produces an error rather than treating true as one.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-react:start */}

```python
observations = []
fixture = {"library_closes": "17:30"}
observations.append({"tool": "lookup", "result": fixture["library_closes"]})
print("actual observation:", observations[-1])
print("next decision input:", observations)
assert observations[-1]["result"] == "17:30"
```

{/* example:e5-react:end */}

Expected mechanism output:

```text
actual observation: {'tool': 'lookup', 'result': '17:30'}
next decision input: [{'tool': 'lookup', 'result': '17:30'}]
```

## When to use it

Use the action-observation loop when external calculations or retrieved facts can improve a task and can be audited. Keep actual tool evidence separate from generated explanations and enforce an explicit stopping policy.

## Limits and common mistakes

A convincing narrative can invent observations. This lab has local fixtures and calculators only, no web navigation or write access. Its restricted action grammar and predeclared operands substantially limit generality; those boundaries are part of the lesson.
