## Definition and intuition

ReAct interleaves reasoning about the next step with tool actions and observations.

Chapter 7 combines model calls with templates, memory, and tools. Trace the inputs and outputs of each step so an error can be located rather than hidden inside a chain.

## Before you start

Read [Agents](/llm-concept-atlas/concepts/agents/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **ReAct** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** State the current question and choose a permitted action
2. **Transform:** Run the tool and treat its result as new evidence
3. **Inspect:** Update the plan or stop with a supported answer.

### The important distinction

ReAct is often described as an alternation of reasoning, action, and observation. The observation must come from the actual tool result, not a fabricated continuation. In a production system, concise internal plans and explicit tool calls are more useful than an unbounded visible reasoning transcript.

## Worked example

To answer store hours, the system decides to search, reads the returned hours page, then answers with that source. If the lookup is empty, it should not invent a time. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
tools = {"lookup": lambda item: {"hours": "5 pm"}.get(item, "unknown")}
plan = [("lookup", "hours")]
for tool, argument in plan:
    print(tool, argument, "->", tools[tool](argument))
```

**Expected output:**

```text
lookup hours -> 5 pm
```

**What the code shows:** The code executes a named tool with an argument and records its observation. A real agent chooses actions dynamically, but application code must still enforce the tool boundary. The [official chapter 7 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter07) develops the corresponding model-based implementation.

## When to use it

Use it for inspectable tool-based workflows where actions depend on observations. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- A trace can still contain wrong assumptions, unsafe actions, or misread tool output.
- **Failure to look for:** A retrieved snippet is mistaken for an instruction and redirects the action plan.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
