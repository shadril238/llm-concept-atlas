## Definition and intuition

A tokenizer vocabulary is the finite mapping between its permitted token units and IDs. A model’s input embedding table uses those IDs as row addresses, so the mapping is part of the model contract.

You swap in a tokenizer with the same number of entries and the model still runs. Shape compatibility hides the error: an ID that used to mean one piece may now select the row associated with another piece.

## How it works

Vocabulary construction trades compact representations of frequent patterns against coverage and sequence length. Whole-word vocabularies need a policy for unseen words; subword vocabularies compose rarer forms; byte-based schemes can represent encodable text through smaller units.

A vocabulary size V and embedding width d give an input table with V × d learned values. Vocabulary size affects both lookup storage and, for many generators, output-head width. The number of active input positions T is a different quantity from V.

Adding a token to a tokenizer changes the encoding mapping. A neural model may also need its embedding/output tables resized and the new rows learned. Merely inventing an ID outside the model’s table can cause an index error; allocating a new row does not supply its meaning.

### The important distinction

Unknown-token behavior can discard information; byte coverage can lengthen sequences.

## Worked example

With vocabulary [cat, dog, [PAD]] and a 2D table [[1, 0], [0, 1], [0, 0]], ID 0 selects [1, 0]. If another tokenizer maps ID 0 to dog, the old model still selects the cat row. Nothing about the integer itself detects the mismatch.

## When to use it

Store tokenizer files and revision beside model artifacts. Check special-token IDs and table shapes before custom training or reload. For multilingual text, inspect coverage and normalization on real inputs rather than assuming a large vocabulary covers every task well.

## Limits and common mistakes

Unknown-token behavior can discard information; byte coverage can lengthen sequences. Similar numeric IDs need not correspond to similar words. Frequency-based vocabulary decisions can reflect corpus biases and make underrepresented scripts less compact.
