## Definition and intuition

Constrained sampling restricts which tokens or structures can be emitted during generation.

Chapter 6 treats a prompt as a task specification. A prompt can guide output, but it does not change model weights or guarantee that an answer is correct.

## Before you start

Read [Output verification](/llm-concept-atlas/concepts/output-verification/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **constrained sampling** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Define an allowed grammar, schema, or token set
2. **Transform:** Mask invalid continuations during decoding
3. **Inspect:** Validate the completed object against semantic rules.

### The important distinction

A grammar or schema can remove invalid tokens from the decoder's next-token choices. This makes certain output shapes impossible to violate, but the model can still choose an incorrect allowed value. Pair decoder constraints with semantic validation and source checks for reliable downstream use.

## Worked example

A generator choosing from `positive` and `negative` cannot produce a third label if the decoder enforces the choice. It can still choose the wrong permitted label. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
allowed = {"positive", "negative"}
candidate = "positive"
print(candidate in allowed)
print("retry or flag" if candidate not in allowed else "accept shape")
```

**Expected output:**

```text
True
accept shape
```

**What the code shows:** Membership in an allowed set checks the shape of one output. It does not determine whether the label was the right one for a particular text. The [official chapter 6 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter06) develops the corresponding model-based implementation.

## When to use it

Use it when machine-readable structure must be reliable. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- A grammar limits form, not truth, relevance, or fair behavior.
- **Failure to look for:** A perfectly valid JSON answer contains an unsupported claim.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
