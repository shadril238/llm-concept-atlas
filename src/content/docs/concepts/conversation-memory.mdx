## Definition and intuition

Conversation memory is application-managed state supplied to later model calls. The model sees the selected messages or summaries in its current context; it does not automatically retain an unlimited conversation between stateless calls.

Memory has at least two questions: what information survives the policy, and what answer the model produces from that information. A fact present in the input can still be ignored, and a fluent summary can lose a crucial correction.

## How it works

### One conversation, three policies

L11 uses one original eight-message conversation for buffer, recent-window, and running-summary policies. The user states a project code, changes the meeting from Friday to Monday, and specifies metric units. The final task asks for those three fields. Policy comparison uses the same source IDs and native tokenizer rather than changing the conversation for each condition.

### Budgeted assembly

The application budgets 192 or 384 total tokens and reserves 64 for output. The native runtime context is separately 768. It drops an optional summary first if it cannot fit, then removes complete oldest user/assistant pairs until the rendered prompt plus reserve fits. The artifact records policy omissions, budget evictions, retained IDs, summary presence, and actual input tokens.

### Retention and use differ

Literal fact presence is a diagnostic, not an answer metric. Each actual model call returns a string-field object graded against the original code, current day, and units. A stale Friday mention can coexist with the Monday correction. Summaries are generated in two real calls and may distort or omit information; their outputs are preserved instead of replacing them with ideal notes.

## Worked example

At the larger recorded budget the full buffer answers all three fields correctly. The recent window retains only later turns and answers fewer fields. The generated summary loses or distorts information and performs worse. This is an observation about one weak model and conversation, not a universal ordering of memory policies. A correct value absent from the supplied evidence can be a coincidence; it does not prove faithful recall.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-conversation-memory:start */}

```python
messages = [
    "u1: code LARK-27",
    "a1: noted",
    "u2: Friday, metric",
    "a2: noted",
    "u3: correction Monday",
    "a3: noted",
    "u4: blue paint",
    "a4: noted",
]
print("buffer:", messages)
print("two recent turn pairs:", messages[-4:])
assert "LARK-27" not in " ".join(messages[-4:])
```

## When to use it

Use explicit memory policies for ongoing assistants with bounded context. Preserve stable message IDs and evaluate both older facts and later corrections before choosing a policy.

## Limits and common mistakes

Context capacity is finite and token counts depend on the actual model renderer. A summary is generated evidence, not a lossless database. Production applications may need explicit structured state, retrieval, correction rules, and separate tests.
