## Definition and intuition

Reinforcement learning from human feedback (RLHF) uses human preference information to shape a policy that generates responses. A conventional pipeline first instruction-tunes a policy, fits a reward model to preferences, and then optimizes generated responses against that reward with controls on drift from a reference policy.

## Theory: how it works

### Policy, reference and reward roles

The policy is the trainable conditional distribution over completions. A reference is a fixed comparison distribution, often the SFT starting policy. A reward model scores prompt/completion pairs using learned preferences. In actor–critic implementations a value model estimates expected return to reduce policy-gradient variance; it is not the same as the reward model or the reference. Sharing architectures or checkpoint origins does not merge their conceptual roles.

An illustrative objective maximizes expected reward minus beta times a KL-divergence penalty from the reference. A larger penalty discourages some distributional drift but does not guarantee safety or truth. The reward signal is imperfect, and optimization can exploit it: highly confident verbose text may score well while failing the task. A reference controls one kind of change; it cannot repair biased preference labels.

### PPO for RLHF

Proximal Policy Optimization (PPO) collects responses from a policy snapshot, scores them, estimates advantages relative to a value baseline, and applies a clipped policy-ratio objective. The old rollout policy used in the PPO importance ratio and the fixed SFT reference used in a KL penalty have different jobs. Reusing “reference” to describe both hides a major implementation distinction.

For positive advantage A=2, ratio 1.3 and clip epsilon 0.2, the surrogate uses min(1.3×2,1.2×2)=2.4. The clipping limits the incentive for this sample's large update; it does not impose a hard global bound on model behavior. Negative advantages use the same min expression and need their sign considered. The small code traces both signs. It is conceptual arithmetic only, not a PPO implementation or training record.

### The important distinction

Preference alignment is a broader umbrella than this conventional RLHF pipeline. DPO optimizes offline chosen/rejected examples with a reference-relative classification objective, without training or querying a separate reward model in the loop. Human labels can be replaced by rule/model judgments, but their origin should then be named accurately. E8's preference defects are rule-authored; calling them broad human alignment would overstate the evidence.

## Worked example

A document assistant starts with an SFT model. Reviewers compare two completions for the same source question; a grounded answer is preferred over an unsupported guess. The reward model learns that ranking. A PPO-style policy could then generate fresh answers, receive scalar scores and update under a drift penalty. Evaluation must still independently check source-grounded answers.

L23 executes the reward-training step, then demonstrates a separate DPO alternative initialized from the saved SFT checkpoint. It does not execute the PPO policy loop, an actor–critic value model or a broad human preference study. This boundary prevents a scalar calculator from masquerading as full RLHF.

## Implement it

This standalone Python 3 calculation uses only the standard library. It does not download or train a model. The [complete generation labs](/llm-concept-atlas/labs/generation-adaptation/) provide the pinned environments, actual training entrypoints, staged notebooks, raw results and artifact checks.

```python
epsilon, ratio = 0.2, 1.3
clipped = max(1 - epsilon, min(1 + epsilon, ratio))
for advantage in [2.0, -2.0]:
    surrogate = min(ratio * advantage, clipped * advantage)
    print("advantage", advantage, "PPO surrogate", surrogate)
print("Old rollout policy ratio differs from a fixed-reference KL penalty.")
```

## When to use it

Use a conventional RLHF pipeline when reward feedback and on-policy generation justify its complexity and you can evaluate reward hacking. Consider offline preference methods when fixed paired data fit the task. Neither route replaces appropriate data review, factual evaluation or fresh test sets; the most easily optimized reward can be the wrong objective.

## Limits and common mistakes

The evaluated instruction subset has 32 training,8 validation and 8 test source contexts. Pretraining overlap is unknown. Repeated views of these test outputs are not a new independent benchmark. Preserve failed and length-limited answers, exact base/tokenizer identity and data provenance when transferring the workflow.
