## Definition and intuition

Instruction prompting specifies the task and output contract in the model input. It conditions generation without updating model weights, and it must be evaluated on actual outputs rather than on how clear the instruction sounds.

“Be accurate” does not specify what a program should parse. A testable instruction identifies the input, permitted output shape, and what to do when information is missing. It still leaves the language model responsible for following the request.

## How it works

### State a verifiable task

L09 uses original arithmetic questions and order-extraction messages with design/evaluation splits. The arithmetic answer is checked using a complete integer or a terminal Answer: integer line under a predeclared parser. Requested-format validity is measured separately. A narrative that a human might interpret but that this parser cannot extract is marked unextractable; the metric is not a comprehensive semantic judgment.

### Control what else changes

Prompt comparisons use the same Q8 artifact, greedy configuration, output caps, and case IDs. Six arithmetic variants and three extraction variants are reported rather than choosing a winner on the evaluation set. Instructions, examples, and requested format can interact. The extraction instruction-only and native-schema conditions use identical messages, isolating the added native decoding constraint.

### No weight update

The model uses the current prompt as input and predicts a continuation. Neither a better instruction nor a new demonstration is gradient training. The application may retain the instruction template for later calls, but that persistence belongs to the application. A model can still ignore, misunderstand, or incompletely satisfy a concise request.

## Worked example

For a contract “one integer only”, the output “Answer: 15” contains an extractable answer but violates the requested bare-integer format. The output “15” meets both shape and content requirements for the seven-plus-eight case. The output “14” meets the shape requirement but is wrong. Three different outcomes need separate checks.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-instruction-prompting:start */}

```python
import re

expected = 15
for raw in ["15", "14", "Answer: 15"]:
    valid = re.fullmatch(r"-?\d+", raw) is not None
    normalized = int(raw.removeprefix("Answer: "))
    print(raw, "format:", valid, "answer:", normalized == expected)
```

{/* example:e5-instruction-prompting:end */}

Expected mechanism output:

```text
15 format: True answer: True
14 format: True answer: False
Answer: 15 format: False answer: True
```

## When to use it

Use instruction prompting as a measured baseline before adding examples, additional calls, or search. A simple task-specific contract is easier to test and debug than a broad request for generally better answers.

## Limits and common mistakes

Formatting requests are not grammar masks. Low sampling randomness does not make a wrong answer correct. The local model can fail elementary tasks; inspect the original outputs and the exact grading policy before interpreting a zero score.

## Check your understanding

<details>
<summary>Can a valid integer be an incorrect answer?</summary>

Yes. Format validation answers whether the output fits the contract; a reference answer or independent verifier checks the task result.

</details>

<details>
<summary>Does changing an instruction fine-tune the checkpoint?</summary>

No. It changes the supplied input. Model weights remain fixed in these workflows.

</details>
