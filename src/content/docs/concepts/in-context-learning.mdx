## Definition and intuition

In-context learning uses task descriptions or demonstrations inside the current input to influence a model’s predictions, without updating its weights. Which examples appear and how they are ordered are part of the input contract.

A model can imitate an example’s format while failing its underlying task. Showing two arithmetic demonstrations does not prove that it learned a general arithmetic algorithm. Inspect both the examples and the generated answer.

## How it works

### Examples live in context

Each demonstration contributes tokens and role boundaries. A user question followed by an assistant demonstration communicates both a task mapping and a response style. The application reconstructs those messages for every call. They do not become persistent weight changes merely because the model responds differently.

### Selection and order

L09 predeclares a balanced addition/subtraction example pair, its reversed order, and an addition-only pair. They use design IDs only. The evaluation questions are identical across conditions. Compare format following, extracted answers, and token work; do not silently select the best evaluation condition and report it as an untouched test result.

### What a comparison can establish

Ordering can change an output even when the same two examples are present. The source records example IDs and complete prompts so the difference can be inspected. One small run does not reveal a universal primacy/recency law, nor does it establish how a larger model would behave. A longer prompt also changes context usage and prefix processing work.

## Worked example

Two demonstrations both end with 5, even though one is addition and one subtraction. A small model may copy 5 on later questions instead of solving them. The balanced pair is not label-balanced in the sense of a classifier dataset, and its repeated answer is a real limitation worth inspecting rather than hiding. Reversed-order and different-answer design examples help reveal these sensitivities.

## Implement it

Run this small standard-library mechanism with Python 3. It illustrates the stated contract or calculation. The connected L09–L11 source below performs the actual local-model workflow; this short snippet is not a substitute for those model calls.

{/* example:e5-in-context-learning:start */}

```python
design = [("2 + 3", 5), ("9 - 4", 5)]
for order in [design, list(reversed(design))]:
    print("demonstrations:", order)
    print("evaluation input:", "7 + 8")
assert all(question != "7 + 8" for question, _ in design)
```

## When to use it

Use demonstrations when they clarify an unfamiliar mapping, domain convention, or desired response style. Version their IDs and compare them against an instruction-only baseline with a fresh evaluation set.

## Limits and common mistakes

Examples can encode misleading patterns or use most of the token budget. Reordering them is not a guaranteed improvement. The atlas keeps all reported variants visible and makes no broad learning-capability claim from this small CPU experiment.

## Check your understanding

<details>
<summary>Why not include the evaluation answer as a demonstration?</summary>

That leaks the target into the input and invalidates the claimed held-out comparison. Demonstrations come from the separate design split.

</details>

<details>
<summary>If the model copies the right format but a wrong number, what did the result show?</summary>

It showed format following under that input, not reliable task generalization. The two metrics must remain separate.

</details>
