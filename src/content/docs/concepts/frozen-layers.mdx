## Definition and intuition

Frozen layers keep selected pretrained weights fixed while other parameters learn a new task.

Chapter 11 adapts an encoder to labeled tasks. Data splits, frozen versus trainable weights, and task-specific heads change both cost and generalization.

## Before you start

Read [BERT fine-tuning](/llm-concept-atlas/concepts/bert-fine-tuning/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **frozen layers** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Choose which backbone layers to freeze
2. **Transform:** Compute features through those layers without updating their weights
3. **Inspect:** Train a task head or remaining layers and compare cost and accuracy.

### The important distinction

When a layer is frozen, its parameters still participate in the forward pass, but the optimizer does not update them. The trainable head can only separate what the fixed features already encode. Gradually unfreezing upper layers is one way to trade compute for adaptation when a head-only baseline is inadequate.

## Worked example

A ticket classifier freezes the encoder and trains only a small head. Training is cheaper, but if ticket jargon is poorly represented the head cannot repair the missing features. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
weights = {"encoder": 0.5, "head": 0.2}
gradients = {"encoder": 0.4, "head": -0.3}
trainable = {"head"}
for name in trainable:
    weights[name] -= 0.1 * gradients[name]
print(weights)
```

**Expected output:**

```text
{'encoder': 0.5, 'head': 0.23}
```

**What the code shows:** Only names in `trainable` receive a gradient update. The frozen encoder value remains fixed, while the task head changes. The [official chapter 11 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter11) develops the corresponding model-based implementation.

## When to use it

Use freezing when compute or data is limited and pretrained features are already suitable. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- Too much freezing limits adaptation; too little can overfit or cost more.
- **Failure to look for:** The head cannot distinguish two classes because the fixed encoder maps them to nearly identical vectors.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
