## Definition and intuition

BERTopic is a modular topic-modeling pipeline that commonly combines embeddings, dimension reduction, clustering, and topic representations.

Chapter 5 explores unlabeled collections. A cluster is a geometric grouping, while a useful topic also needs an interpretable description and inspection by a person.

## Before you start

Read [Topic modeling](/llm-concept-atlas/concepts/topic-modeling/) first. You should be able to explain what information its output carries. Then return here and ask what extra problem **BERTopic** solves. This sequence matters because a plausible output can hide a missing prerequisite or a weak input representation.

## Theory: how it works

1. **Prepare:** Embed documents with a suitable encoder
2. **Transform:** Reduce dimensions and cluster similar vectors
3. **Inspect:** Build topic words and representative examples, then inspect them.

### The important distinction

The familiar BERTopic recipe uses an embedding encoder, UMAP for dimension reduction, HDBSCAN for clustering, and class-based TF-IDF for topic words. Each stage can be replaced, which is a strength but also means a change upstream can alter every reported topic. Inspect outliers and representative documents after each change.

## Worked example

A collection of research abstracts is embedded, reduced with UMAP, grouped with HDBSCAN, and labeled with distinctive terms. Replacing the embedding model can change every later stage. Walk through the three stages above with that input: identify what is prepared, what changes, and which observation would show success. Then change one condition in the example. If the conclusion changes, the method is sensitive to that choice; if it does not, ask whether the example actually tests the mechanism.

## Implement it

**Setup:** Python 3; no packages or API key are needed. Save the following as `example.py` and run `python3 example.py`. It is a small deterministic illustration of the relevant calculation or data flow. It does not download a trained model.

```python
documents = ["rain storm cloud", "sun warm beach", "cloud rain wind"]
groups = [0, 1, 0]
for group in sorted(set(groups)):
    words = [word for text, label in zip(documents, groups) if label == group for word in text.split()]
    print(group, sorted(set(words), key=lambda word: (-words.count(word), word))[:3])
```

**Expected output:**

```text
0 ['cloud', 'rain', 'storm']
1 ['beach', 'sun', 'warm']
```

**What the code shows:** Documents are grouped first, then common words are counted within each group. Real topic pipelines use more careful term weighting and human inspection. The [official chapter 5 notebook](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models/tree/main/chapter05) develops the corresponding model-based implementation.

## When to use it

Use it when semantic embeddings and inspectable topic representations are useful for an unlabeled collection. Choose it when the input and output in your application match those assumptions. Compare the simplest useful baseline first, then measure whether the additional complexity improves the metric that matters to readers or users. Record the model, data version, and decision threshold when applicable so results can be reproduced.

## Limits and common mistakes

- Its modularity makes defaults convenient but does not make topics objective or stable.
- **Failure to look for:** A topic appears meaningful only because a reduction or clustering parameter changed the neighborhood structure.

A teaching demo usually holds data and model behavior fixed so one mechanism is visible. Real systems face noisy inputs, changing distributions, and edge cases. Test examples that should fail as well as examples that should succeed, and inspect the intermediate stage that causes the error.
